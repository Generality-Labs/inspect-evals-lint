### Added

- `metric_epoch_safety` (IEBP014) checks custom metrics against the scores Inspect actually hands them. By default the epoch reducer runs before every metric, even at `epochs=1`: `value` can be an epoch mean such as 0.667, and `answer`, `explanation` and `reason` are `None` unless every epoch agrees. The rule reads each `@metric` function, including the function it returns and helpers nested in it, and each `@score_reducer`. It reports an error for `.as_int()`, `.as_bool()` or `int(...)` of anything computed from a score value in a metric, but not `int(len(...))` or `int()` of a comparison. It warns on a single-type `isinstance(v, int)` or `isinstance(v, float)` applied directly to a score value; `(int, float)` and the `isnan` guard are fine. It reports an error for reading `<x>.score.answer`, `.explanation` or `.reason` in a metric, and for an attribute or subscript assignment into the scores a metric or reducer was handed. Names are followed in statement order, so rebinding one to a deep copy ends it, and a store into a field that a shallow `model_copy()` shares with the original is flagged. `@metric(scores="unreduced")` metrics see raw epoch scores, so only the last check applies to them. The hints recommend converting each value with `value_to_float()`, as `accuracy()` and `mean()` do, which holds under every reducer. `Score.as_float()` raises on `"C"`, and a type filter drops samples under `mode` or `max`. Nothing is followed into plain helper functions or other files ([#58](https://github.com/Generality-Labs/inspect-evals-lint/issues/58)).
