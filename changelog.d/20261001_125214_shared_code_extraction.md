### Added

- `shared_code_extraction` (IECQ006) warns where an evaluation extracts code from a completion with its own fence pattern instead of `inspect_evals.utils.code.extract_code_block`. It flags a string literal holding a triple-backtick fence, or a regex quantifier for three backticks, passed as the pattern to `re.compile`, `search`, `findall`, `finditer`, `match`, `fullmatch` or `sub`, or as a tag to `extract_from_tags`. As the separator to `split`, `replace`, `find`, `partition` or `startswith` it counts only with a language label, so a bare fence toggle while reading markdown does not warn. F-strings, `+` concatenations and names bound to a literal in the same function or at module level count, including a name inside a concatenation. There is one warning per function, and one for a file's module-level patterns. A pattern whose fences are all labelled `json` is left alone, and so is a bare closing fence beside one in the same function. A `(?:json|python)?` alternation still warns. Test files and the helper's own module are not read. The rule applies only where the helper is available: a helper package defines `extract_code_block` (inspect_evals itself), or the root `pyproject.toml` declares `inspect-evals` outside `dev`. Elsewhere it is skipped. The docs say a migration needs a task version bump, and that an evaluation whose upstream benchmark takes a different block should suppress with a reason. On inspect_evals main it warns at 17 functions in 15 evaluations. Six are covered by open migration PRs; scicode's fix in UKGovernmentBEIS/inspect_evals#2326 keeps a local regex and still warns ([#62](https://github.com/Generality-Labs/inspect-evals-lint/issues/62)).
